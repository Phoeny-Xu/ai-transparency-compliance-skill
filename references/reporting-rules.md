# 报告写作细则（reporting-rules）

> 用途：本文件承载 SKILL.md 阶段4「报告硬性要求」的细则，供三个模板（modeA-report-template / modeB-research-review-template / modeB-comparison-template）共用，避免同一规则在 SKILL.md 与模板间多处复制。主文件只留摘要（SKILL.md §3 阶段4）；与底线 L1–L6 的对应关系在各节标注。本文件为 SKILL.md v1.1 的伴生文件。

## 一、义务表述底线（对应 L2/L3/L4/L6）

1. **已确定 / 待核实区分**：义务清单区分「已确定义务」与「待核实（条件式）义务」；关键事实（covered provider 的系统访问规模是否达到适用门槛、large online platform 此前12个月逐月独立用户是否达到门槛、是否构成相应角色等）未解决时，不得写成无条件义务，须以「若X成立则触发Y」条件式表述，并在第一节列「待核事实清单」（逐条「待核事实 → 若成立则触发义务 → 待核人/材料」）。B3a与B4_2c属于不同法律口径，除非统计对象、地域、周期、去重方法和用户集合均一致，不得互相替代或据档位差异认定矛盾。
2. **证据等级标注**：每项结论/义务注明证据来源等级——法条原文引用 / 规则库静态整理 / 规则推演（条件式）/ 实测结果；禁止把「规则推演」描述成「实测结果」。
3. **法规要求与落地建议严格分列**：建议部分标注「建议措施」，不得与法定义务混写。
4. **义务措辞**（L3）：强制性「应当」、非强制「建议」/「可以」。
5. **脚注格式**（L4）：脚注引官方原文＋条号（欧盟/加州英文、中国中文）；正文对应条号处有上标锚点（如「根据《互联网信息服务深度合成管理规定》第16条[^cn16]」），无孤儿脚注（文末有定义、正文无上标引用标记视为不规范）；凡以「含……」「等」概括性表述开头、或仅复述规则库摘要的脚注，一律替换为完整官方原文。
6. **效力核验记录**（L6）：每部被引法规一行「法规名：效力状态，核验于{日期}，来源」。**全称与简称系同一份文件**：同一部法规的正式全称与通行简称是同一份文件（如《互联网信息服务深度合成管理规定》与「深度合成规定」、《生成式人工智能服务管理暂行办法》与「暂行办法」），效力核验只做一次、效力表只占一行，不得因正文出现两种写法而重复核验或重复列行。

## 二、结构组织

1. 义务按「价值链环节×法域」组织，同一环节三地义务并排呈现。
2. 每项义务含五要素：义务内容、法条锚点（经阶段3核验）、生效/适用日期、责任主体、未合规后果。
3. 附三地罚则对比。
4. 角色判定结论附推理依据（双锚定，见 role-mapping.md）。
5. **重点概要前置**：报告先给结论与要点概览，再展开具体义务论述（先概括，后具体）。
6. **法定术语与释义**：三地义务主体使用各地法定术语（中国：深度合成服务提供者等；欧盟：provider/deployer；加州：covered provider 等），首次出现时附中文释义。
7. **现状盘点节（B10，位于§一角色判定之后）**：机械列示问卷 B10 已填报的「已实施」透明度标识措施，并据已识别义务主题给出结构化「待补齐」提示（建议层，非法律结论）；属事实/建议层，不替代法律判断；A3 为空（纯分析型）不生成该块；未采集 B10 时注明「未采集现状盘点」，不得留空误导为「已全覆盖」。该节内容由 `scripts/build_skeleton.py` 据 `survey_audit.json` 的 `B10_current_practices` 机械生成，agent 据实补全待补齐项对应的义务主题，最终以第三节义务详述为准。**自述≠已验证**：现状列一律标「自述，待核验」，差距项给「核验证据」动作（如取样核验界面提示、抽查元数据），不得据自述直接写「已合规」。**一致性复核（防伪矛盾）**：仅「实施状态类答案」（B2(a)＝是／B4①申请渠道＝有／用户自然语言描述）与 B10 自述可构成矛盾；义务触发信号（A3模态／B1形态／B4②运营平台／B6发布编辑行为／A4a量级）与 B10=尚未实施 的组合属报告差距节的常态内容，**不是矛盾**，不列入复核。

## 三、正文洁净（对应 L5）

1. **去个性化**：正文（含章节标题、表格单元格、段落）不出现——问卷编号（A1、A3、B1①、B5a、B8③、B9 等）、价值链环节编号（环节①/②/③…）、内部流程术语（阶段2/阶段3、回填确认、问卷）。改用法律术语/法定主体名称/业务活动描述，例：
   - 「模型自研自训」「应用服务提供」「网络信息内容传播服务」代替「环节①/③/④」；
   - 「算法备案与安全评估」代替「B8备案+安全评估」。
   问卷编号仅允许出现在报告末尾「批注（判断过程、思路与假设）」章节（及 .docx 批注气泡）。
2. **禁 blockquote 承载推理**：正文（含标题前导语、表格说明、小节开头）不得用 `>` 引用块承载问卷回填、主体确认、前置判断、合并规则、体系化组织说明、角色间义务关系说明、SB 1000 提示等 agent 推理/组织过程——此类内容写入末尾「批注」章节。
   - **`>` 的使用边界（★强制，2026-09-15 定，机器检查码 `E-04`）**：仅**报头声明区**（文档主标题之下、首个二级标题之前）可用 `>` 承载生成日期、法规时效声明、依据、范围声明等元数据；**正文（自首个二级标题起）一律禁用 `>`**，正文声明性内容（含未覆盖维度与转介卡、落地建议节导语）一律以普通段落或表格呈现。理由：正文灰色引用块会被读者误认作法规原文引文。
   - 落地建议节如需提示读者「本节属建议措施」，写成加粗普通段落；其余属于对写作者的要求（如合并规则、「禁止只列空泛建议」）一律移入 `<!-- 【指令】 -->` 注释，不进交付物。
   - 「批注」章节内的 `>` 不受此限（该节交付 .docx 时转为 Word 批注、不进正文）。
3. **排版三分离**：生成指令（★强制规则、自检引用、「本表硬性规则」等）仅存于 SKILL.md 与模板 `<!-- -->` 注释，不入交付物；判断过程/推理/假设归「批注」节。交付 .docx 时调用 `scripts/annotations_to_docx_comments.py` 将该节转为真实 Word 批注（comments）并从正文移除；交付 Markdown 时批注节保留文末并标注内部参考。
4. **报头声明区是术语豁免区（★强制，2026-09-15 定）**：`scripts/lint_terms.py` 的 W 级检查（W-20 禁用词、W-21「标识」越界）**不适用于报头声明区**，含范围声明、法规时效声明、依据、生成日期、临近节点提示等行。理由：范围声明与依据系模板强制照搬或元数据，其原文里就含「溯源数据」等中国法定术语（GB 45438），对其中用词报错等于要求违反「范围声明原样照搬」。
   - 边界与 E-04 共用同一条线（首个二级标题之前），不另立一套判定；
   - 范围声明既可写成 `>` 块、也可写成普通段落，两种形态都在豁免范围内（按内容信号识别）；
   - 报头区的**要点概览、未覆盖维度与转介卡**系自主撰写，不属声明区，仍受全部检查；
   - **批注节**同样免于 W 级检查（判断过程留痕，交付为 Word 批注），但硬禁用词「鲁棒」`[E-20]` 在批注节仍生效；
   - 代码或规则若需调整扫描范围，以本条的「声明区／正文」划分为准，不得在脚本里另立第二套口径。

## 四、中国法义务体系化组织

1. 涉及标识义务的内容按义务类型组织为「总体要求→显式标识→隐式标识」。
2. 同一义务类型内关联条文**合并同项**，禁止拆分为多个独立义务点：
   - 《互联网信息服务深度合成管理规定》第16条 与 《人工智能生成合成内容标识办法》第5条 → 均指向隐式标识，合并；
   - 第17条第1款 与 标识办法第4条 → 均指向显式标识，合并。
3. 其它非标识义务同样遵循「关联条文合并同项」。
4. 〔非透明度义务〕条目（如实名认证、内容审核、算法备案、安全评估）在详述节标题加「（非透明度义务）」后缀。
5. 算法备案/安全评估以法律术语呈现法定触发结论（如「算法备案与安全评估法定触发结论」），各条目标「法定触发状态」；触发推理（三项客观事实检验、例外出口）归入批注，正文不出现「B8」编号。

## 五、欧盟 CoP 义务就地扫描与分点论述

0. **落位规则（★）**：凡报告考虑欧盟法下义务之处，均须先扫描《AI生成内容透明度行为准则》（CoP）并输出其对应的行为准则义务；**任何模式均不得另设独立的「CoP 措施要点展开」章节**（2026-09-19 用户裁定：CoP 随欧盟义务就地展开，不单独成节）。落位按模式区分——**模式B 对比报告**：①对比矩阵欧盟列标 CoP 编号（C× M×.×）＋层级标签＋该维度的措施要点摘要；②第五节「企业合规义务梳理」各主体项下，表格之后逐条详述该主体相关的 CoP 措施。**模式B 单法域梳理**：义务清单设「行为准则对应（欧盟适用）」列，并在各主体第5小节「成文法义务与行为准则义务的衔接」内逐条展开。**模式A**：落位于分法域义务详述的欧盟节。某维度或主体无对应措施时显式写「无对应措施」并说明原因（如仅涉 Art. 50(1)/(3)，不在准则覆盖范围），不得留白，亦不得虚构挂钩。
1. CoP 对应措施按「义务类型（Commitment分组）」分点展开，每组一个分点、组内逐条展开措施要点，禁止一句话一条、整段堆砌。
2. 每条措施含：要求内容、技术/操作要点、来源、层级标签（will/encouraged/may）——**四要素缺一不可**。
3. 关键要点不得省略：M1.1 元数据+水印多层方案、M1.2 标记不可移除、M2.1 免费提供、M3.4 互操作性 2027-02-02 节点。
4. 展开前必读 `references/cop-digest.md`；逐字引用或 digest 未覆盖处按其锚点定位 sources txt 原文，不得只搬 eu-rules.md 速查表。
5. 单法域梳理下每个欧盟义务主体另设第5小节「成文法义务与行为准则义务的衔接」，说明 Art. 50 义务与 CoP Measure 的具体对应；通用法律地位（自愿承诺、证明作用、不构成合规推定/确凿证据、Measure 层级以原文动词为准）统一在「二、义务主体与义务内容」开头总述，不逐主体重复。
6. **固定注册表＋个案矩阵**：`cop-digest.md` 的 `cop_case_registry/1` 固定登记25个规则单元，不因产品删减；报告编写者以 `assets/cop-case-matrix-template.json` 建 `cop_case_matrix/1`，按个案角色与Art.50触发结论确定 `relevant_sections`，相关Section每项只能分类为 `applicable`／`conditional`／`not_applicable`／`to_verify`。后三类均写理由；矩阵不进正式正文，结论摘要落批注。
7. **签署事实与法律义务分层**：模式A矩阵的 `signatory` 必须逐字取自 `B11_cop`；未签署、计划签署或不确定不得写成已承担准则承诺，但均不改变Art.50成文法义务。模式B无具体签署主体时写「不确定」并留空Section，不作事实推定。
8. **机器覆盖标记**：适用/条件适用的will或commit+will正文后加 `cop:item` HTML注释；仅正文已实质覆盖的点才能列入 `points`。S1-C1-M1.1、S1-C1-M1.2、S1-C3-M3.4须覆盖注册表全部 `required_points`。这些注释仅供转docx前校验，转换时剥离。
9. **建议闭环**：个案已触发的三地全部义务写入矩阵 `triggered_obligations`；每个建议主题以 `cop:recommendation` HTML注释列出所覆盖义务ID。每个适用CoP项及每个 `triggered_obligations` 项至少出现一次，不得以两三条空泛建议代替覆盖。
10. **转docx前门禁**：先跑 `validate_cop_coverage.py <矩阵>.json <报告>.md`；模式A追加 `--audit <survey_audit.json>`。0E/0W方可转换，脚本只查闭环、不替代适用性法律判断。

## 六、加州结论三类状态与分层

1. **三类状态区分**：covered provider / GenAI hosting platform / large online platform / capture device manufacturer 按下列三类分别表述，禁止混为一框：
   - ①**当前不触发（主体资格未达）**：如 covered provider 的 GenAI 系统未达当前版本门槛（待签署期：月活未达100万，§22757.1(d)；SB 1000 生效后：不在加州公开可访问，§22757.1(e)）、或纯文本不在 §22757.2/§22757.3 范围 → 现行法明确不属于。
   - ②**已适用、义务待生效**：hosting platform（§22757.3.2，2027-01-01）、large online platform（§22757.3.1，2027-01-01）、capture device manufacturer（§22757.3.3，2028-01-01）→ 现行法定义即可判定构成，义务延缓至指定日，单列「已适用、义务待生效（YYYY-MM-DD）」并给出生效日前落实节点。
   - ③**若适用**：其他附条件情形。
   三类标题前缀、责任主体表述、法域开头声明须与各自状态匹配，不得用统一「以下义务当前不触发」涵盖。
2. **多原因不触发分层**：同时具备「主体门槛未达」（主导/阈值原因）与「输出模态不在 §22757.2/§22757.3 范围」（层级抗辩）两类原因时，先写主体门槛，再写「退一步，即便构成 covered provider，本案纯文本输出亦不落入义务范围」；禁止括号并列（如「（纯文本且非 covered provider）」）。
3. **已适用待生效 vs 主体资格未达分列**：两类不并列（前者现行法已构成角色仅义务延缓、后者现行法明确不属于该角色）；SB 1000 前瞻提示仅附着「主体资格未达」类，不外溢至「已适用、义务待生效」类（hosting platform/large online platform/capture device manufacturer 定义不受 SB 1000 影响）。
4. **SB 1000 状态开关**：签署状态核验与义务基准切换见 `references/ca-rules.md`「〇、效力状态开关」；确定性修订对照见 `references/sb1000-diff.md`。

## 七、中英双语段段对应

用户选「中英双语」时，正文须满足以下覆盖，任一中文单元无英文对照即不达标：

1. **叙事段落 1:1**：每中文叙事段落紧跟对应英文，中文用自然法律用语、英文用原文术语。
2. **标题双语**。
3. **表格双语**：表头中英并列；单元格关键法律/技术术语附英文，或另附并行英文表。
4. **元数据字段值双语**：责任主体/优先级/未合规后果/生效日期/技术细则等结构化字段的值中英并列（如「深度合成服务提供者（deep-synthesis service provider）」），不得以「字段名已双语」替代「值未译」。
5. **批注章节**：转 Word 批注后可仅中文，正文须干净。
6. **脚注**：承载法条原文者免译；agent 附加解释性脚注须双语。

**常见缺陷模式（须避免）**：仅译显式/隐式/算法备案等首句、跳过画像段与总体要求与实名认证/内容审核/投诉举报/全部加州条目/落地建议段，且表格单元格与元数据 bullet 全程无英文——此为非达标，须补全至段段对应后方可交付。

## 八、落地建议综合论述

1. 第五节「落地建议」综合前文（第二、三节）已触发的全部义务论述。
2. 按「义务主题」跨法域组织；三地/两地通用义务合并为同一主题（先列明各地义务来源、再给统一落地措施）。
3. 禁止只列两三条空泛建议、或按法域重复堆叠。

## 九、法条原文与分析评论分节（模式B）

1. 对比矩阵单元格只放经核实的法条内容（带条文锚点）。
2. 差异评析、研究观察单独成节，防止读者把分析当立法原文。
3. 多法域对比须含「相同点、不同点、共通要求与单法域特别规定」汇总（分（一）相同点/共通要求、（二）不同点/制度分歧、（三）单法域特别规定）。
